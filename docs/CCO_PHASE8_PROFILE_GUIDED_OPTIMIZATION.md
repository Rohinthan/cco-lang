# Cco Compiler — Phase 8: Profile-Guided Optimization & Backend Refinement

## 1. Executive Summary & Architecture

Phase 8 introduces a deterministic, lightweight, profile-guided optimization (PGO) subsystem and native backend refinement to the Cco compiler. Building directly on the Phase 5 SSA foundations, Phase 6 SSA optimizations (SCCP, GVN/CSE, LICM), and Phase 7 Interprocedural Analysis (IPA/Call Graph), Phase 8 bridges runtime execution measurements with compiler optimization passes.

The optimization philosophy adheres to strict principles:
- **Conservative Decision Making**: A profile represents observed sample execution, not proof of dead or unreachable code. Zero-count branches or blocks are never deleted; instead, they guide layout hints, inlining thresholds, and register allocation without affecting program correctness.
- **Fail-Safe Fallback**: Missing, empty, or malformed profile files fail gracefully to standard non-PGO optimization passes with informative warnings, never halting compilation or generating corrupt binaries.
- **Deterministic Compilation**: Profile serialization and all profile-driven transformations are strictly ordered and independent of hash-table iteration, host pointer ordering, or nondeterministic file system timestamps.
- **Zero Overhead in Standard Mode**: Profile collection instrumentation is completely isolated to `--profile-generate` compilation and leaves normal compilations untouched.

## 2. Profiling Infrastructure & Deterministic Format

### Profile Format Specification: `CCO_PROFILE_V1`

The profile format is human-readable, version-tagged, and deterministically sorted. All function and block names follow the deterministic names generated by Cco IR lowering.

```text
CCO_PROFILE_V1

function main 1
function calc_arith 2000000

block main.entry 1
block calc_arith.entry 2000000
block calc_arith.while.cond.1 2000001
block calc_arith.while.body.2 2000000
block calc_arith.while.end.3 2000000

branch calc_arith.while.cond.1 true 2000000
branch calc_arith.while.cond.1 false 1

loop calc_arith.while.cond.1 1 2000000
```

### Supported Profile Directives

| Record | Syntax | Description |
|---|---|---|
| Header | `CCO_PROFILE_V1` | Version header ensuring forward and backward compatibility. |
| Function | `function <name> <count>` | Execution count of function entries. |
| Block | `block <fn>.<bb> <count>` | Basic block entry frequency. |
| Branch | `branch <fn>.<bb> <true\|false> <count>` | Taken branch count for conditional branches. |
| Loop | `loop <fn>.<header> <entries> <iterations>` | Loop entry and total iteration counts. |

## 3. Profile-Guided Inlining Engine

Phase 8 expands the Phase 7 static inlining cost model with dynamic execution weights:

$$\text{Effective Threshold} = \begin{cases} 
\min(\text{Threshold} + 30, 80) & \text{if call site is HOT} \ (\text{count} \ge 1000 \lor \text{count} \cdot 10 \ge \text{max}) \\ 
15 & \text{if call site is COLD} \ (\text{count} = 0 \lor \text{count} \cdot 1000 < \text{max}) \\ 
\text{Threshold} & \text{otherwise (WARM / Static)} 
\end{cases}$$

### Inlining Guards & Hard Ceilings
1. **Hard Size Ceiling ($\le 80$ IR instructions)**: Large functions are strictly barred from inlining even if executed billions of times, preventing instruction cache thrashing.
2. **Recursive Function Protection**: Functions involved in direct or indirect recursive cycles (SCC size $> 1$) are never inlined.
3. **PGO Transparency Log**: The `--dump-inlining` flag dumps detailed rationales for every candidate call site.

## 4. Trace-Based Basic Block Code Layout

In standard block ordering, conditional branches jump on condition true to the `then` target and fall through to the `else` target. If the `then` branch is taken 99.9% of the time, the CPU branch predictor experiences taken-branch penalties.

Phase 8 implements `ir_cfg_reorder_blocks_for_layout`:
1. Identifies biased conditional branches using profile data where taken frequency exceeds $80\%$.
2. Places the hot successor block immediately adjacent to the conditional block.
3. The native instruction generator and peephole optimizer invert the conditional jump condition (`jne` -> `je`) to jump to the cold target on failure, allowing the hot path to fall through without jump penalties.

## 5. Native x86-64 Backend Refinement & Peephole Optimizations

The peephole optimization engine in `src/x86_64_instr.c` was expanded to eliminate machine-level inefficiencies:
1. **Redundant Register Moves**: Eliminates self-moves (`mov %rax, %rax` and `movsd %xmm0, %xmm0`).
2. **Zero-Immediate Optimization**: Replaces 32-bit and 64-bit zero loads (`mov $0, %rax`) with `xor %eax, %eax`, saving 5 bytes per occurrence and breaking CPU register dependency chains.
3. **Store-then-Load Elimination**: Redundant loads immediately following a store to the same stack slot are eliminated.
4. **Redundant Fall-Through Jump Elimination**: Unconditional jumps (`jmp .L1`) immediately preceding label `.L1:` are deleted.
5. **Inverted Conditional Branch Optimization**: Replaces `jcc .L1; jmp .L2; .L1:` with `jncc .L2; .L1:`.
6. **Jump-to-Jump Chain Collapse**: Collapses jump chains (`jmp .L1` where `.L1:` immediately jumps to `.L2`).
