# Cco x86-64 Backend Phase 3B: Internal ELF64 Static Linker & Final Executable Generation

## 1. Phase Objective & Architectural Evolution

Phase 3B achieves a critical milestone in the self-sufficiency of the Cco compiler: **direct executable generation without invoking `gcc`, `ld`, or any external host linker**.

```text
Phase 1:
Cco Source → AST → Semantic Analysis → Cco IR → IR Verification → C11 Codegen → GCC/Clang → Executable

Phase 2A–2D (Native Instruction Lowering & System V AMD64 ABI):
Cco Source → AST → Scope → Cco IR → CFG Liveness → Linear Scan Allocator (GPR + XMM) → Assembly (.s) → GNU as → Host Linker → Linux Executable

Phase 3A (Direct Machine-Code Encoding & Object Writer):
Cco Source → Cco IR → Dual-Class Regalloc → Unified X86InstrList → Machine Encoder → ELF64 Object Writer → Relocatable Object (.o) → Host Linker → Linux Executable

👉 Phase 3B (Internal ELF64 Static Linker & Direct Standalone Executable Generation):
Cco Source → Cco IR → Dual-Class Regalloc → Machine Encoder → ELF64 Relocatable Object (.o)
                                                                       │
                                                                       ▼
                                                       ┌───────────────────────────────┐
                                                       │       Cco ELF64 Linker        │
                                                       │ ├─ Object Reader & Validator  │
                                                       │ ├─ Global Symbol Resolver     │
                                                       │ ├─ Section Merger (.text/.ro) │
                                                       │ ├─ Virtual Memory Layout      │
                                                       │ ├─ Relocation Engine (PC32)   │
                                                       │ ├─ W^X Segment Builder        │
                                                       │ └─ Standalone Startup Runtime │
                                                       └───────────────┬───────────────┘
                                                                       │
                                                                       ▼
                                                          Standalone Linux ELF64 Binary
                                                          (Zero GCC, Zero LD, Zero AS)
```

With Phase 3B complete, Cco is capable of compiling high-level Cco code directly to native Linux executables entirely using internal code generation, machine encoding, and static linking.

## 2. Linker Input Specification (Phase 3A Object Format)

The Cco internal linker consumes standard System V AMD64 relocatable object files (`ET_REL`, `EM_X86_64`) generated by Phase 3A:
* **Headers**: `Elf64_Ehdr` with `e_type = ET_REL`, `e_machine = EM_X86_64`, `ELFCLASS64`, `ELFDATA2LSB`.
* **Executable Code (`.text`)**: Byte buffer containing encoded x86-64 instructions, 16-byte aligned.
* **Read-Only Constants (`.rodata`)**: String literals, jump tables, and IEEE 754 floating-point literals, 16-byte aligned.
* **Relocations (`.rela.text`)**: Array of `Elf64_Rela` entries specifying offset, target symbol index, and signed addend (`r_addend`).
* **Symbols (`.symtab` & `.strtab`)**: Strict local-first symbol partitioning (`STB_LOCAL` section and file symbols followed by `STB_GLOBAL` defined and undefined symbols).

## 3. Linker Architecture & Core Components

The static linker is implemented in [`src/x86_64_link.h`](file:///home/raccoon/cco-lang/src/x86_64_link.h) and [`src/x86_64_link.c`](file:///home/raccoon/cco-lang/src/x86_64_link.c).

### 3.1 Object Reader & Defensive Validation
`elf64_read_object_file` and `elf64_read_object_memory` defensively parse and validate input objects:
1. **Magic & Header Checks**: Verifies `\x7fELF`, `ELFCLASS64`, `ELFDATA2LSB`, `ET_REL`, and `EM_X86_64`.
2. **Buffer Bounds Checks**:
   - Asserts section header table does not extend past EOF (`e_shoff + e_shnum * e_shentsize <= raw_size`).
   - Asserts every section data span lies strictly within file bounds.
3. **Symbol & Relocation Sanity**:
   - Asserts symbol names are bounded within `.strtab`.
   - Asserts every relocation offset $r\_offset < \text{size}(.text)$ and target symbol index is valid.

### 3.2 Symbol Collection & Resolution
The linker manages a unified global symbol table:
* **Global Definitions**: Tracks virtual addresses, sizes, defining object index, and section association.
* **Duplicate Detection**: Multiple strong global definitions of the same symbol across input objects trigger an immediate descriptive error (`duplicate strong definition of symbol '...'`).
* **Undefined Symbol Resolution**: Every undefined symbol reference (`SHN_UNDEF`) is matched against defined global symbols. Unresolved symbols produce descriptive errors.

### 3.3 Section Merging & Alignment
Compatible sections across multiple object files are merged into contiguous buffers:
* **Executable Code (`.text`)**:
  - Each object's `.text` is appended at an aligned 16-byte boundary:
    $$\text{offset\_in\_merged\_text}[k] = \text{align}(\text{current\_size}, 16)$$
  - Pad bytes between functions are filled with `0x90` (`NOP`).
* **Read-Only Data (`.rodata`)**:
  - Each object's `.rodata` is appended at an aligned 16-byte boundary.
  - Zero-padded to preserve literal alignment.

### 3.4 Virtual Memory Layout & W^X Enforcement
The executable memory space uses standard Linux x86-64 page-aligned segments:

```text
Virtual Address Space:
0x400000 ┌────────────────────────────────────────────────┐  Segment 0: PT_LOAD (R--)
         │ ELF64 Header + Program Headers (Phdr Table)    │  Size: <= 0x1000
0x401000 ├────────────────────────────────────────────────┤  Segment 1: PT_LOAD (R-X)
         │ Merged .text (Executable Machine Instructions) │  Size: ceil_page(text_size)
         │ + Standalone Startup Runtime (_start, printf)  │
0x402000 ├────────────────────────────────────────────────┤  Segment 2: PT_LOAD (R--)
         │ Merged .rodata (Strings, IEEE 754 Floats)      │  Size: ceil_page(rodata_size)
         └────────────────────────────────────────────────┘
         PT_GNU_STACK: Flags RW- (Enforces Non-Executable Stack)
```

* **W^X Compliance**: Executable memory (`R-X`) is never writable. Data and headers are never executable (`R--`).
* **Page Alignment**: Every `PT_LOAD` segment satisfies the Linux kernel requirement:
  $$\text{p\_vaddr} \pmod{0\text{x}1000} == \text{p\_offset} \pmod{0\text{x}1000} == 0$$

### 3.5 Relocation Engine
Phase 3B processes the relocation types emitted by the Cco compiler:
* **`R_X86_64_PC32`**: 32-bit PC-relative displacement to data.
* **`R_X86_64_PLT32`**: 32-bit PC-relative displacement to call targets.

For every relocation at byte offset $O$ in merged `.text`:
1. Calculate place virtual address:
   $$P = \text{TEXT\_VADDR} + O$$
2. Identify target symbol virtual address $S$:
   - For `.rodata` section symbols: $S = \text{RODATA\_VADDR} + \text{obj\_rodata\_offset}[k] + \text{st\_value}$.
   - For local functions: $S = \text{TEXT\_VADDR} + \text{obj\_text\_offset}[k] + \text{st\_value}$.
   - For global functions: $S = \text{resolved\_global\_symbol}\to\text{vaddr}$.
3. Calculate signed displacement:
   $$V = S + A - P$$
4. Overflow check: Asserts $-2^{31} \le V \le 2^{31}-1$.
5. Patch: Writes 32-bit signed integer in little-endian byte order into `.text` buffer.

## 4. Standalone Startup Runtime

To execute without relying on external `libc.so` or dynamic loaders, Cco embeds a minimal, pure Linux x86-64 assembly runtime ([`src/runtime_start.s`](file:///home/raccoon/cco-lang/src/runtime_start.s)):

1. **`_start` Entry Point**:
   - Clears `%rbp` (`xorq %rbp, %rbp`) to mark the outermost stack frame.
   - Extracts `argc` from `(%rsp)` into `%rdi`.
   - Computes `argv` pointer (`leaq 8(%rsp), %rsi`).
   - Ensures 16-byte stack alignment.
   - Invokes `call main`.
   - Moves return value `%rax` to `%rdi` and executes `SYS_exit` (`syscall 60`).
2. **`printf` Minimal Formatter**:
   - Formats integers (`"%ld\n"`), strings (`"%s\n"`), and floats (`"%g\n"`) without `libc`.
   - Issues direct Linux `SYS_write` (`syscall 1`) to file descriptor 1 (`stdout`).
3. **`malloc` & `free` Bump/Mmap Allocator**:
   - Allocates memory pages using Linux `SYS_mmap` (`syscall 9`).
   - `free` is a safe no-op.

If an input object already provides `_start` or custom runtime symbols, the linker links the user's symbols without injecting defaults.

## 5. Multi-Object Linking & CLI Support

### 5.1 Standalone Object Linker (`cco-link`)
```bash
# Link multiple relocatable objects into a final standalone executable
./cco-link main.o helper.o math.o -o program
./program
```

### 5.2 Direct Compiler Invocation
```bash
# Mode B: Compile directly with Cco's internal static linker (No GCC/LD invoked!)
./cco program.cco --use-internal-linker -o program
./program

# Or compile and immediately run
./cco program.cco --use-internal-linker --run

# Mode A: Host linker path preserved as reference
./cco program.cco --use-native -o program
```
